# Comments anchored to objects, and pointing an AI at one element (open question 7)

Scope note: open question 7 in `docs/spec-v0.md` asks how Figma, Google Slides and Pitch anchor comments to objects, and how Gamma and Pitch let a user point their AI at one element. This file also records tldraw, PowerPoint, Canva, Microsoft Copilot, Vercel and GitHub as prior art where the plan's sub-questions name them or the evidence bears on the same design (spec section 5, "Feedback for agents"). Research date: 2026-10-20.

## SQ1: How does Figma anchor comments (canvas coordinates vs node ids, pinned to frames, what happens when the node moves or is deleted, REST API comment model with client_meta node_id and node_offset)?

### REST API model

The REST API exposes six comment endpoints: `GET /v1/files/:key/comments` (optional `as_md` query), `POST /v1/files/:file_key/comments` (body `message`, `comment_id`, `client_meta`), `DELETE /v1/files/:file_key/comments/:comment_id`, and GET, POST and DELETE on `/comments/:comment_id/reactions`. Read scope is `file_comments:read`, write scope `file_comments:write` [source: https://developers.figma.com/docs/rest-api/comments-endpoints | Figma REST API: Comments endpoints | vendor].

The POST body field `comment_id` is "The comment to reply to, if any", and `client_meta` is "The position of where to place the comment", accepting Vector, FrameOffset, Region or FrameOffsetRegion [source: https://developers.figma.com/docs/rest-api/comments-endpoints | Figma REST API: Comments endpoints | vendor].

No REST endpoint to resolve or reopen a comment appears in the endpoint list; the Comment type carries `resolved_at` as read data only [source: https://developers.figma.com/docs/rest-api/comments-endpoints | Figma REST API: Comments endpoints | vendor] [source: https://developers.figma.com/docs/rest-api/comments-types | Figma REST API: Comments types | vendor].

Comment type fields: `id`, `client_meta` ("Positioning information of the comment"), `file_key`, `parent_id` ("If present, the id of the comment to which this is the reply"), `user`, `created_at`, `resolved_at` ("If set, the UTC ISO 8601 time the comment was resolved"), `order_id` ("Only set for top level comments. The number displayed with the comment in the UI"), `reactions` [source: https://developers.figma.com/docs/rest-api/comments-types | Figma REST API: Comments types | vendor]. The fetched page did not list a `message` field (the fetch tool reported it absent from that page; the POST body has `message`).

Replies are flat: one `parent_id` level pointing at a top-level comment [source: https://developers.figma.com/docs/rest-api/comments-types | Figma REST API: Comments types | vendor].

Anchor shapes in `client_meta` [source: https://developers.figma.com/docs/rest-api/comments-property-types | Figma REST API: Comments property types | vendor]:

- `FrameOffset`: `node_id` ("Unique id specifying the frame.") and `node_offset` ("2d vector offset within the frame from the top-left corner.").
- `Region`: canvas `x`, `y`, `region_height`, `region_width` (both "Must be greater than 0"), `comment_pin_corner` (default `bottom-right`; values bottom-right, bottom-left, top-right, top-left).
- `FrameOffsetRegion`: `node_id`, `node_offset`, `region_height`, `region_width`, `comment_pin_corner`.
- `Vector`: plain canvas coordinates (defined on the file property types page, linked from the comments pages).

So Figma's anchor is either absolute canvas coordinates (Vector, Region) or a frame id plus an absolute pixel offset from the frame's top-left corner (FrameOffset, FrameOffsetRegion). The offset is in pixels, not a fraction of the frame [source: https://developers.figma.com/docs/rest-api/comments-property-types | Figma REST API: Comments property types | vendor].

Third-party MCP servers that read Figma comments resolve a `node_id` anchor by direct lookup, but for Vector and Region anchors they search "the deepest node whose bounding box contains the point, flagged as inferred" [source: https://glama.ai/mcp/servers/junsimon/figma-comments-mcp | figma comments mcp (Glama listing) | practitioner]. (Read only as a search-result summary; the listing page was not fetched.)

### In-app behaviour: what is pinned, and what follows a move

Figma Help: "Comments can be pinned to a specific frame or layer, or specific co-ordinates on the canvas." and "You can change where the comment is pinned." [source: https://help.figma.com/hc/en-us/articles/360041547853 | Figma Help: Move or edit comments | vendor].

Cut and paste: "If you cut a layer or frame and paste this in a new location, Figma disconnects the comment from that layer. You can still view and respond to that comment from the right sidebar." Canvas-pinned comments stay at their original coordinates. "Figma won't move comments if you cut and paste layers between files." [source: https://help.figma.com/hc/en-us/articles/360041547853 | Figma Help: Move or edit comments | vendor].

Move to page: "If you use the Move to page option to move a layer within a file, Figma also moves any comments." But "If the comment was linked to the canvas—not the layer or frame itself—Figma won't move the comment." [source: https://help.figma.com/hc/en-us/articles/360041547853 | Figma Help: Move or edit comments | vendor].

Duplicating a file does not copy comments: "Comments are only kept on the original file." [source: https://help.figma.com/hc/en-us/articles/360041547853 | Figma Help: Move or edit comments | vendor].

The help article does not cover deleting a layer that carries a comment, nested layers, or resolving [source: https://help.figma.com/hc/en-us/articles/360041547853 | Figma Help: Move or edit comments | vendor]. No usable source found for what Figma does to a comment when its frame is deleted.

Top-level frames only: Figma Community Support (user "djv", 22 July 2024): "Figma can only pin comments at a set of coordinates on a top-level frame, not any of the nested elements." [source: https://forum.figma.com/suggest-a-feature-11/keep-comments-pinned-to-design-elements-including-nested-17753/index14.html | Forum: Keep comments pinned to design elements including nested | practitioner].

The feature request dates from June 2021: "When i move my design elements/frames/etc., I expect all the pinned comments to move with them – but they don't." (Maya Shendelman, 9 June 2021) [source: https://forum.figma.com/t/keep-comments-pinned-to-design-elements-including-nested/4632?page=8 | Forum: Keep comments pinned (page 8) | practitioner]. Other 2021 posts in the same thread: when "the design above a comment changes, the comment becomes disassociated" (Erin-UX, 5 Oct 2021); comments "do not stay attached" when frames move across pages (Ashley_Chozas, 1 Dec 2021); one user asked for a choice between floating and pinned comments (Ben_Smeets, 30 June 2021) [source: https://forum.figma.com/t/keep-comments-pinned-to-design-elements-including-nested/4632?page=8 | Forum: Keep comments pinned (page 8) | practitioner].

Still open in 2025 and 2026: "Clients comments can't still be pinned on an element" (Alexis_Dam-Van, 14 Nov 2025); "I expect all the pinned comments to move with them – but they don't." (Vincent Abou Ghazale, 26 Jan 2026); a user reports a workaround keeps comments on non-top-level frames and asks Figma "to allow comment authors to pin directly to a specific frame or element" (Weier_Matt, 10 Oct 2025). No Figma staff reply appears on that page [source: https://forum.figma.com/suggest-a-feature-11/keep-comments-pinned-to-design-elements-including-nested-17753/index16.html | Forum: Keep comments pinned (page 16) | practitioner].

Contradiction: Figma Community Support said in November 2023, "My comments are moving with the frames," and "We're not able to reproduce this issue on our end." (Gayani_S, 15 Nov 2023; ksn, 29 Nov 2023) [source: https://forum.figma.com/t/help-comments-are-broken-not-fixed-to-a-frame/57730 | Forum: Help, comments are broken, not fixed to a frame | practitioner]. Read together with the July 2024 reply, the support statements are consistent with comments following top-level frames but not nested layers; the forum does not state this in one place.

### Dev Mode annotations (layer-bound notes, a separate primitive from comments)

Figma blog on Dev Mode GA: "Since annotations are connected to a layer on the canvas, any property or measurement will change as designs change." and "With the plugin API, teams can build custom Dev Mode plugins to create and manage annotations in bulk." [source: https://www.figma.com/blog/dev-mode-ga/ | Figma blog: Dev Mode GA | vendor].

Plugin API type: `interface Annotation { readonly label?: string; readonly labelMarkdown?: string; readonly properties?: ReadonlyArray<AnnotationProperty>; readonly categoryId?: string }`. The node field `annotations` ("Annotations on the node.") exists on 11 node types: ComponentNode, ComponentSetNode, EllipseNode, FrameNode, InstanceNode, LineNode, PolygonNode, RectangleNode, StarNode, TextNode, VectorNode [source: https://developers.figma.com/docs/plugins/api/Annotation | Figma Plugin API: Annotation | vendor].

So Figma has two models side by side: comments sit beside the document and point at a top-level frame by id plus pixel offset; annotations are stored on the node itself and follow it [source: https://developers.figma.com/docs/rest-api/comments-property-types | Figma REST API: Comments property types | vendor] [source: https://developers.figma.com/docs/plugins/api/Annotation | Figma Plugin API: Annotation | vendor].

## SQ2: How do Google Slides (Drive API comments with anchor, object-level comments, what the API exposes) and Pitch (comments on slides and blocks, mentions, resolve) anchor comments to objects, and what happens to comments when the object changes?

### Google Drive API comments (the older, generic path)

Drive API: an anchored comment "is tied to a specific location within a specific version of a document"; "Developers can define their own format for the anchor specification." Google editor apps "don't render comments created with the Drive API anchored to content" and treat them as unanchored [source: https://developers.google.com/workspace/drive/api/guides/manage-comments | Drive API: Manage comments | vendor].

Drive API anchors are immutable and may not hold across revisions; Google recommends them for files whose content does not move, such as images or read-only documents [source: https://developers.google.com/workspace/drive/api/guides/manage-comments | Drive API: Manage comments | vendor].

For editor files, "the `anchor` field contains editor-specific internal anchor data (such as a `workbook-range` JSON string on Sheets files)", which the Drive API treats as opaque; it cannot resolve slide elements [source: https://developers.google.com/workspace/drive/api/guides/manage-comments | Drive API: Manage comments | vendor].

Drive comment fields include `anchor` ("A region of the document represented as a JSON string."), `quotedFileContent`, `resolved` (output only), `replies[]`, `mentionedEmailAddresses[]`, `assigneeEmailAddress` [source: https://developers.google.com/workspace/drive/api/reference/rest/v3/comments | Drive API v3: comments resource | vendor]. A comment is resolved only by posting a reply with an `action`; `resolved` is read-only on update; the `fields` parameter is mandatory for the comments resource [source: https://developers.google.com/workspace/drive/api/guides/manage-comments | Drive API: Manage comments | vendor].

### Google Slides API comments (new in 2026, anchored to object ids)

Timeline: Google's release notes record "The Google Slides API now supports reading, creating, replying to, updating, and deleting comments" as a Developer Preview on 31 Aug 2026, and "The Docs, Sheets, and Slides MCP servers in Developer Preview can now read comments via an optional commentsIncluded field" on 1 Oct 2026 [source: https://releases.sh/sources/src_7aLBPByE36fG9UEb8vh_n | releases.sh tracker of Google Workspace release notes (citing developers.google.com/workspace/release-notes#August_31_2026 and #October_01_2026) | practitioner]. The Google release-notes page itself was not fetched.

The Workspace Updates blog (30 Sep 2026): "Developers can now programmatically create, read, and manage comments across Google Docs, Sheets, and Slides." Slides comments are "comments associated with individual slides and specific presentation elements." Comment support in the Docs, Sheets and Slides MCP servers "remains in developer preview in accordance with the preview status of the MCP servers." Rollout: "Gradual rollout (up to 15 days for feature visibility) starting on September 30, 2026"; available to all Workspace customers and personal accounts; no admin control [source: https://workspaceupdates.googleblog.com/2026/09/programmatic-comment-and-suggestion.html | Workspace Updates: Programmatic comment and suggestion support | vendor].

Reading: comments are omitted by default; set `commentsViewMode` to `COMMENTS_VIEW_MODE_INCLUDED` on `presentations.get` or `pages.get` (or `COMMENTS_VIEW_MODE_DEFAULT_FOR_CURRENT_ACCESS`). The response carries `comments` (CommentThread objects) and `commentAnchors` (CommentAnchor objects that map anchor ids to page or page element locations) [source: https://developers.google.com/workspace/slides/api/guides/comments | Slides API: Manage comments | vendor]. With default-for-access mode, a view-only user gets `COMMENTS_VIEW_MODE_OMITTED`; `INCLUDED` returns 403 without comment permission (search-result summary of the CommentsViewMode reference) [source: https://developers.google.com/workspace/slides/api/reference/rest/v1/CommentsViewMode | Slides API: CommentsViewMode | vendor].

Writing: `presentations.batchUpdate` with `insertComment` (content plus an anchor). Anchor options: `objectId` (a slide page or a page element such as a shape or table), `shapeTextAnchor` (text range in a shape), `tableCellTextAnchor`, `tableAnchor`. Optional `assigneeEmailAddress` [source: https://developers.google.com/workspace/slides/api/guides/comments | Slides API: Manage comments | vendor].

Replies and resolve: `addCommentReply` with `commentId` and a `post`; the post may carry `commentAction` `RESOLVE` or `REOPEN` and an `assigneeEmail`. `updateCommentPost` edits a post you authored. `deleteComment` removes a whole thread (only by the head post's author); `deleteCommentReply` cannot delete reply posts "that contain a commentAction or an assigneeEmail" [source: https://developers.google.com/workspace/slides/api/guides/comments | Slides API: Manage comments | vendor].

Partial failure: "the presentation model changes... might be successfully committed, but the associated comments might fail to save." The batchUpdate response carries `commentUpdateState`: `NO_UPDATES_REQUESTED`, `ALL_SAVED`, `ALL_FAILED_UNKNOWN_REASON` [source: https://developers.google.com/workspace/slides/api/guides/comments | Slides API: Manage comments | vendor]. Page last updated 2026-09-30.

CommentThread fields: `commentId`, `anchorId` ("The ID of the CommentAnchor in the presentation that this thread is tied to."), `headPost`, `replies[]`, `status` (`OPEN` / `RESOLVED`), `plainTextQuote` ("The quoted text from the page element when the comment was created, formatted as plain-text."). Post fields: `postId`, `content` (non-empty unless the action is RESOLVE or REOPEN; at most 2048 UTF-8 code units), `contentHtml`, `author`, `createTime`, `updateTime`, `deleted`, `fromImportedPresentation`, `fromCopiedPresentation`, `assigneeEmail`, `commentAction` (`NO_COMMENT_ACTION_CHANGE`, `RESOLVE`, `REOPEN`) [source: https://developers.google.com/workspace/slides/api/reference/rest/v1/CommentThread | Slides API: CommentThread | vendor].

Anchor model on the Page resource: `CommentAnchor` "Contains a list of all locations in a `Page` that are anchored to a `CommentThread` via the same `anchorId`." and "Multiple separate anchors may refer to the same location, either within a `Page` or across different pages". Fields `anchorId` and `objectAnchors[]`. `ObjectAnchor` "Represents comment anchor data tied to a Slides object, for example a `Page` or `PageElement`"; `objectId` is "The page or page element that the comment thread is anchored to."; text anchors "Will be empty if the comment anchor is for the entire page or page element rather than a text range within the element." Sub-types `shapeTextAnchors` (ranges) and `tableCellAnchors` (cellRanges with `cellLocation` and `ranges`) [source: https://developers.google.com/workspace/slides/api/reference/rest/v1/presentations.pages | Slides API: presentations.pages | vendor].

So in Google Slides the anchor is an object id (slide or element), optionally narrowed to text ranges, held in a separate anchor list the thread points to by `anchorId`; one anchor id can have several object locations [source: https://developers.google.com/workspace/slides/api/reference/rest/v1/presentations.pages | Slides API: presentations.pages | vendor].

What happens when the object is deleted: the Slides comments guide does not say [source: https://developers.google.com/workspace/slides/api/guides/comments | Slides API: Manage comments | vendor], and the Docs Editors help article on comments does not say either [source: https://support.google.com/docs/answer/65129 | Google Docs Editors Help: Use comments, action items and reactions | vendor]. No usable sources for that angle after two searches.

Google Slides UI (from the shared Docs Editors help article): "Highlight the text, images, cells, slides, or scenes you want to comment on", then Add comment; assign with "@" or "+" plus an email and tick Assign; Resolve sits "In the top corner of the comment"; reopen via "Re-open in the top right corner of the comment"; @mentions send an email [source: https://support.google.com/docs/answer/65129 | Google Docs Editors Help: Use comments, action items and reactions | vendor].

Third-party Google Workspace MCP servers already expose Slides comment tools such as `list_presentation_comments` and `manage_presentation_comment` (create, reply, resolve) [source: https://glama.ai/mcp/servers/taylorwilsdon/google_workspace_mcp/tools/list_presentation_comments | Glama: google_workspace_mcp list_presentation_comments | practitioner]; Arcade's Slides server has `ListPresentationComments` with an `include_deleted` flag defaulting to false [source: https://docs.arcade.dev/mcp-servers/productivity/google-slides | Arcade: Google Slides MCP server | vendor]. (Both read only as search-result summaries; pages not fetched.)

### Beyond SQ2's named products: PowerPoint modern comments (OOXML)

The modern comment element `CT_Comment` (namespace `http://schemas.microsoft.com/office/powerpoint/2018/8/main`, MS-PPTX 2.16.3.3) carries exactly one anchor group (`EG_CommentAnchor`, minOccurs 1, maxOccurs 1): `pc:sldMkLst` ("identifies the slide to which the comment is anchored"), `ac:deMkLst` ("identifies the drawing element to which the comment is anchored"), `ac:txMkLst` ("identifies the text character range"), or `unknownAnchor`. Then `pos` ("the position of the comment, relative to the top-left corner of the first object to which the comment is anchored"), `replyLst`, `txBody`. Attributes include `id`, `authorId`, `status`, `created`, `startDate`, `dueDate`, `assignedTo`, `complete`, `title` [source: https://learn.microsoft.com/en-us/openspecs/office_standards/ms-pptx/161bc2c9-98fc-46b7-852b-ba7ee77e2e54 | MS-PPTX: CT_Comment | vendor].

`ST_CommentStatus` values: `active`, `resolved`, `closed` [source: https://learn.microsoft.com/en-us/openspecs/office_standards/ms-pptx/bd806e3a-96cf-43aa-9618-81b317c34c61 | MS-PPTX: ST_CommentStatus | vendor]. `CT_CommentUnknownAnchor` is "an unknown comment anchor type for future extension" [source: https://learn.microsoft.com/en-us/openspecs/office_standards/ms-pptx/a9085f48-1f4f-4a43-ac93-ecbc91ae1af6 | MS-PPTX: CT_CommentUnknownAnchor | vendor].

The drawing element moniker list "together uniquely identifies a drawing element"; it is a drawing moniker list followed by one of `ac:spMk`, `ac:grpSpMk`, `ac:graphicFrameMk`, `ac:cxnSpMk`, `ac:picMk`, `ac:inkMk` [source: https://learn.microsoft.com/en-us/openspecs/office_standards/ms-odrawxml/145d263b-da8a-4cad-b076-1e51a9d149bf | MS-ODRAWXML: CT_DrawingElementMonikerList | vendor]. A shape moniker carries `id` (the drawing element id) and `creationId` ("a unique creation ID of the shape", a GUID) [source: https://learn.microsoft.com/en-us/openspecs/office_standards/ms-odrawxml/496f12c8-6363-42cb-b75c-90b7c2d9c37f | MS-ODRAWXML: CT_ShapeMoniker | vendor].

User-facing behaviour: comments on objects follow the object, "if you move the object, the comment goes with it"; text anchors tie a comment to "a specified range of text, instead of to an object"; typing inside the range expands it, deleting text shrinks it; resolved threads leave the margin but stay in the Comments pane; older PowerPoint versions cannot read modern comments, and a file shows only one comment type, set by its first comment [source: https://support.microsoft.com/en-us/powerpoint/modern-comments-in-powerpoint | Microsoft Support: Modern comments in PowerPoint | vendor].

Deleted text anchor: "If the entire highlighted text is deleted, the comment will attach to the object the text was in." This sentence comes from a search-result snippet of the Microsoft 365 Insider blog; the page itself redirected and the archived copy was rate-limited, so it was not read [source: https://insider.microsoft365.com/blog/do-more-with-modern-comments-in-powerpoint | Microsoft 365 Insider blog: Do more with modern comments in PowerPoint | vendor] [inaccessible].

Cut and paste (May 2025, Windows v2503 build 18623.20178 and later, Mac v16.96 build 25041326 and later): comments follow a cut-and-pasted object; "The original keeps its comment; the copy starts fresh"; cut without paste leaves "the comment ... on the original slide" [source: https://office-watch.com/2025/powerpoints-comments-stick-like-glue/ | Office Watch: PowerPoint's comments stick like glue | journalism]. A Neowin report on the same change returned 403 and was not read [source: https://www.neowin.net/news/microsoft-makes-it-easier-to-keep-comments-when-editing-powerpoint-presentations/ | Neowin | journalism] [inaccessible].

### Beyond SQ2's named products: tldraw comments (SDK v5.3, 2026)

tldraw blog "A comment is not a shape" (Jessica Edwards, 6 Aug 2026): comments ship as `@tldraw/commenting`; a thread is a separate record holding a pointer to its target; "The drawing doesn't know the comments exist."; the pin position is stored as a fraction of the shape "rather than a fixed point" (a "normalized anchor"); anchor kinds are a point, a shape, a region around several shapes, or the whole page; "a text-range anchor was prototyped and cut"; on delete the comment "drops an anchor at exactly the spot the pin was sitting and stays there"; undo of the delete re-attaches the pin unless it was moved in the meantime, in which case "your placement wins" [source: https://tldraw.dev/blog/a-comment-is-not-a-shape | tldraw blog: A comment is not a shape | vendor].

Source code (package `@tldraw/commenting` 5.5.2, read 2026-10-20) defines the anchor union exactly [source: https://github.com/tldraw/tldraw/blob/main/packages/tlschema/src/records/TLComment.ts | tldraw: packages/tlschema/src/records/TLComment.ts | vendor]:

```ts
export type TLCommentAnchor =
	| { type: 'shape'; shapeId: TLShapeId; x: number; y: number; isPrecise: boolean }
	| { type: 'point'; x: number; y: number }
	| { type: 'region'; x: number; y: number; w: number; h: number; pinX?: number; pinY?: number }
	| { type: 'page' }
```

Same file: the thread owns the anchor and resolution state (`resolved: { at: number; by: string } | null`); messages are separate `TLComment` records pointing at the thread by `threadId`; "v1 threads are flat — no nested replies"; threads are "excluded from document snapshots and `.tldr` exports server-side, and persisted in a separate lane from the main document", gated by `objectAccess` "so 'can comment but not edit' is expressible"; `isDeleted` is a soft delete, write-once and creator-only; comment mutations "are deliberately not undoable" to avoid "a comment reappearing after someone else deleted it" [source: https://github.com/tldraw/tldraw/blob/main/packages/tlschema/src/records/TLComment.ts | tldraw: TLComment.ts | vendor].

Anchor lifecycle code: "When the shape is deleted, the thread converts to a `point` anchor where its pin last sat"; "When the shape moves to another page, the thread follows"; "When a deleted shape comes back, the thread re-attaches — unless its pin was manually moved in the meantime"; remote changes are ignored because "the client that performed the operation runs this same maintenance and syncs the result" [source: https://github.com/tldraw/tldraw/blob/main/packages/commenting/src/canvas/anchor-lifecycle.ts | tldraw: packages/commenting/src/canvas/anchor-lifecycle.ts | vendor].

Shape anchor detail: `x`, `y` are "normalized (0–1) within the shape's bounds"; with `isPrecise: false` the pin sits at the `impreciseShapeAnchor` option (default top-right) and refers to the shape as a whole [source: https://tldraw.dev/examples/comment-anchors | tldraw example: Comment anchors | vendor] [source: https://tldraw.dev/reference/tlschema/TLCommentAnchor | tldraw reference: TLCommentAnchor | vendor].

Contradiction: the v5.3.0 release notes say "threads anchor to a point, a shape (precisely or imprecisely), a text range, a region, or the page." [source: https://tldraw.dev/releases/v5.3.0 | tldraw v5.3.0 release notes | vendor], while the blog says text range was cut [source: https://tldraw.dev/blog/a-comment-is-not-a-shape | tldraw blog: A comment is not a shape | vendor] and the source union has no text-range variant [source: https://github.com/tldraw/tldraw/blob/main/packages/tlschema/src/records/TLComment.ts | tldraw: TLComment.ts | vendor].

### Research on pointing plus language

IEEE VR 2025 study (Chen, Grubert, Kristensson; 12 participants) of LLM-assisted 3D scene editing with speech and raycast pointing: P7, "Raycast enabled precision control, when I want to select, deselect a specific object"; P8, "The speech recognition is much faster than selecting objects with raycast"; reference failure, P7, "I selected a particular book and asked it to change book to purple, but the system changed all the books."; P7 asked the system to "factor in my gaze or selections to provide further context." Bulk Modification share of time rose from M=.194 (Task 1) to M=.465 (Task 2).
