### Authoring syntax

- Slides are split by `---` "padded with a new line"; each slide is a Markdown section [source: https://sli.dev/guide/syntax | Slidev: Syntax Guide | vendor].
- YAML frontmatter at the start of a slide configures it; "The first frontmatter block is called **headmatter** and can configure the whole slide deck" [source: https://sli.dev/guide/syntax | Slidev: Syntax Guide | vendor].
- "The comment blocks at the end of each slide are treated as the note of the slide"; comments elsewhere are not notes [source: https://sli.dev/guide/syntax | Slidev: Syntax Guide | vendor].
- Vue components and HTML can be written directly in a slide, with UnoCSS classes for styling [source: https://sli.dev/guide/syntax | Slidev: Syntax Guide | vendor].
- Headmatter defaults: `theme: default`, `aspectRatio: 16/9`, `canvasWidth: 980`, `presenter: true`, `exportFilename: slidev-exported`, drawings enabled and not persisted by default [source: https://sli.dev/custom/ | Slidev: Configurations | vendor].

### Layouts and slots

- A slide picks its layout with `layout:` in frontmatter; the first slide defaults to `cover`, the rest to `default` [source: https://sli.dev/guide/layout | Slidev: Layout | vendor].
- Layouts are Vue components; load order is built-in, then theme, then addon, then the deck's own `layouts/` directory, and "the last one loaded will override the previous ones" [source: https://sli.dev/guide/layout | Slidev: Layout | vendor].
- Built-in layouts: `center`, `cover`, `default`, `end`, `fact`, `full`, `image-left`, `image-right`, `image`, `iframe-left`, `iframe-right`, `iframe`, `intro`, `none`, `quote`, `section`, `statement`, `two-cols`, `two-cols-header` [source: https://sli.dev/builtin/layouts | Slidev: Built-in Layouts | vendor].
- Slot sugar: "We also provide a shorthand syntactical sugar `::name::` for slot name"; content after `::right::` fills the right slot, and `::default::` can be given explicitly to reorder [source: https://sli.dev/features/slot-sugar | Slidev: Slot Sugar for Layouts | vendor].

### Click animations and transitions

- One click is one step. `v-click` (directive or `<v-click>` component) hides content until the step; `v-after` appears with the previous click; `.hide` hides on click [source: https://sli.dev/guide/animations | Slidev: Animations | vendor].
- `v-clicks` applies `v-click` to each child list item, with `depth` and `every` options [source: https://sli.dev/guide/animations | Slidev: Animations | vendor].
- Positions: relative values are quoted with a sign (`at="+2"`, `v-click="'-1'"`, default `'+1'`); plain numbers are absolute; `v-click.hide="[2, 4]"` gives a range with an exclusive end; `clicks: 10` in frontmatter sets the slide's total [source: https://sli.dev/guide/animations | Slidev: Animations | vendor].
- Effect presets: `fade`, `fade-in`, `up`, `down`, `left`, `right`, `scale`, `none`, combinable as `v-click.fade.right`; per-slide default via `clickAnimation:` [source: https://sli.dev/guide/animations | Slidev: Animations | vendor].
- `v-motion` with `:initial`, `:enter`, `:click-1`, `:click-2-4` variants; caveat: "only `v-click` on the same element as `v-motion` controls the motion" (paraphrase by fetch tool) [source: https://sli.dev/guide/animations | Slidev: Animations | vendor].
- Slide transitions set by `transition:` (built-ins `fade`, `fade-out`, `slide-left`, `slide-right`, `slide-up`, `slide-down`, `view-transition` experimental); forward and back can differ (`go-forward | go-backward`); custom ones are CSS classes [source: https://sli.dev/guide/animations | Slidev: Animations | vendor].

### Free positioning (`v-drag`)

- Draggable elements: `v-drag="'square'"` names a position in frontmatter `dragPos`, or `v-drag="[Left,Top,Width,Height,Rotate]"` inline; `<v-drag pos="...">` component form; position is a comma string of five values [source: https://sli.dev/features/draggable | Slidev: Draggable Elements | vendor].
- The docs warn that Slidev uses "regex to update the position value in the slide content", and recommend the frontmatter form if problems occur [source: https://sli.dev/features/draggable | Slidev: Draggable Elements | vendor].
- Controls: double-click to start dragging, arrow keys move, Shift keeps ratio, click outside to stop; `<v-drag-arrow />` for arrows [source: https://sli.dev/features/draggable | Slidev: Draggable Elements | vendor].
- Bug report: `<v-drag>` with `pos` appended `undefined` to the tag in the Markdown file while dragging (Slidev 0.50.0-beta.7, closed) [source: https://github.com/slidevjs/slidev/issues/1959 | Issue 1959: v-drag with pos appends "undefined" | practitioner].
- In issue 2365, a maintainer answer says an empty line is required before `<v-drag-arrow />` "to make sure the new position is written back to your markdown file correctly" [source: https://github.com/slidevjs/slidev/issues/2365 | Issue 2365: Draggable Elements has no effect | practitioner].

### Editing UI and presenter mode

- UI page lists a "Toggle Integrated Editor" action, a notes editor at `/notes-edit` that autosaves, and note editing in slide overview; it does not describe a visual layout editor [source: https://sli.dev/guide/ui | Slidev: User Interface | vendor].
- Presenter mode at `/presenter` shows the current slide with notes and next-slide preview; navigating there makes "all other opened pages ... automatically follow" [source: https://sli.dev/guide/ui | Slidev: User Interface | vendor].

### Export

- PDF default at `./slides-export.pdf`; `--format png` writes one PNG per slide; "By default, Slidev exports one page per slide with clicks animations disabled", and `--with-clicks` exports each step as a page; a browser export UI exists, best in Chromium [source: https://sli.dev/guide/exporting | Slidev: Exporting | vendor].
- `--format pptx`: "Note that all the slides in the PPTX file will be exported as images, so the text will not be selectable." "Presenter notes will be conveyed into the PPTX file on a per-slide basis." `--with-clicks` is on by default in this mode [source: https://sli.dev/guide/exporting | Slidev: Exporting | vendor].
- Image pptx export first merged 2024-05-25 as PR 1603 "feat: export to PPTX" [source: https://github.com/slidevjs/slidev/pull/1603 | PR 1603: export to PPTX | vendor].
- `--format pptx-editable`: exports "with native shapes instead of pictures" so "text is selectable and editable, boxes can be moved and recolored, and presenter notes are carried over"; "This does not replace `--format pptx`, which stays the most visually faithful option"; "What stays a picture: anything PowerPoint has no equivalent for" [source: https://sli.dev/guide/exporting | Slidev: Exporting | vendor].
- Per the same page (fetch-tool summary): SVG (so Mermaid and icons), canvas, iframes, video, KaTeX, CSS gradients, `filter`, `backdrop-filter`, `mix-blend-mode` and `clip-path` stay pictures; fonts are referenced, not embedded; text may wrap onto a different number of lines; `::before`/`::after` decorations are dropped and listed; `--per-slide` is not supported [source: https://sli.dev/guide/exporting | Slidev: Exporting | vendor].
- PR 2722 "feat(export): editable PPTX export with native shapes and text", +5,051 lines, merged 2026-09-16T00:23Z [source: https://github.com/slidevjs/slidev/pull/2722 | PR 2722: editable PPTX export | vendor].
- Method, from the PR body: it "walks the rendered DOM at export time and emits native shapes and text boxes rather than one picture per slide"; files `walker.ts` (in-page facts), `normalize.ts` (pure functions over JSON), `color.ts`, `capture.ts` (Playwright), `build.ts` (writes `.pptx` through `pptxgenjs`); 115 tests over fixtures and unzipped OOXML [source: https://github.com/slidevjs/slidev/pull/2722 | PR 2722: editable PPTX export | vendor].
- Numbers on `demo/starter`, from the PR body: `slide1.xml` 770 bytes vs 5,134 bytes; 0 vs 640 shapes; 0 vs 1,554 text runs (image vs editable) [source: https://github.com/slidevjs/slidev/pull/2722 | PR 2722: editable PPTX export | vendor].
- What PR 2722 does not do: "No template or `.potx` loading, no slide master synthesis, no font embedding"; "No gradients: `pptxgenjs` has none, so they rasterize"; "A long paragraph can wrap onto a different number of lines, because PowerPoint's text metrics are not Chromium's"; dashed underline drawn solid by PowerPoint [source: https://github.com/slidevjs/slidev/pull/2722 | PR 2722: editable PPTX export | vendor].
- Fallback: a slide that "throws, times out, loses all its text, or comes out more than 60% picture with nothing recovered over it falls back to exactly today's `--format pptx` output, for that slide alone" [source: https://github.com/slidevjs/slidev/pull/2722 | PR 2722: editable PPTX export | vendor].
- Testing claim in the PR: run over four themes the author did not build against; "Twenty-six distinct defects came out of that, each now a named test" [source: https://github.com/slidevjs/slidev/pull/2722 | PR 2722: editable PPTX export | vendor].
- Click steps in pptx are exported as separate static slides; open PR 2758 says "Both PPTX formats export click steps by default, but the CLI reference says false" and documents "static click steps" for editable export [source: https://github.com/slidevjs/slidev/pull/2758 | PR 2758: correct editable PPTX defaults and limitations (open) | vendor].
- Follow-up open PR 2757 "fix(export): preserve image fitting and opacity in editable PPTX" [source: https://github.com/slidevjs/slidev/pulls?q=pptx | Slidev PR search (GitHub API, 2026-10-20) | vendor].

Contradiction: pkgpulse (2026-05-16) lists Slidev exports as "Static web build and PDF/image export" and says "PPTX is not the core use case; if PowerPoint handoff is mandatory, Marp is usually simpler" [source: https://www.pkgpulse.com/guides/slidev-vs-marp-vs-revealjs-code-first-presentations-2026 | Slidev vs Marp vs reveal.js 2026 | practitioner]. Slidev's docs and PR 1603 (merged 2024-05-25) show pptx export existed before that date; editable pptx came after it (2026-09-16) [source: https://github.com/slidevjs/slidev/pull/1603 | PR 1603 | vendor].

Contradiction: Slidev docs and PR 2758 disagree on the `--with-clicks` default for pptx in the CLI reference (PR 2758 is open, not merged) [source: https://github.com/slidevjs/slidev/pull/2758 | PR 2758 | vendor].

### Slide model

### How agents fare writing Typst

- TeXFix-Bench (repair, not generation; 10,437 instances; seven LLMs; 48,651 attempts): compile rate over all attempts Markdown 90.2%, LaTeX 74.2%, Typst 60.3%; among API-ok attempts 99.9%, 85.5%, 77.7%; "per-model Typst CRitt spans 42.8–86.1%"; authors say the gap "is consistent with newer syntax and less public training mass, though we do not observe training corpora directly" [source: https://arxiv.org/html/2608.07617 | TeXFix-Bench (Venkateshmurthy, arXiv 2608.07617, 2026-08-07) | independent].
- TeXFix-Bench abstract: "Typst is markedly harder than LaTeX and Markdown" and "Compile success alone overstates repair quality" [source: https://arxiv.org/abs/2608.07617 | TeXFix-Bench abstract | independent].
- TypstBench (forum, 2025-05-14): 23 tasks, no docs in context, outputs compared by MD5 of the PDF; Gemini 2.5 Pro 65.22%, Claude 3.7 Sonnet 60.87%, Claude 4.5 Haiku 56.52%, Gemini 2.5 Flash 56.52%, GPT-4.1 21.74%, GPT-4.1-Mini 8.70%; author: "The dataset contains only 23 basic tasks atm" [source: https://forum.typst.app/t/benchmarking-llms-on-typst/4085 | Benchmarking LLMs on Typst | practitioner].
- Counter-evidence on TypstBench method: commenter quachpas: "The md5 hash of a pdf file is not a reliable way to check the output difference"; another notes GPT models output "Markdown and LaTeX syntax or just made-up Typst-like syntax" [source: https://forum.typst.app/t/benchmarking-llms-on-typst/4085 | Benchmarking LLMs on Typst | practitioner].
- Typst forum (2024-10-24): "getting working Typst code is a lot more difficult due to the lack of training data and constant breaking changes" (pixelpanda); Claude's Typst "usually contains some errors and requires minor adjustments" (ParaN3xus); cetz diagrams harder than TikZ for ChatGPT (Bryn) [source: https://forum.typst.app/t/llm-code-generation/1331 | LLM code generation? | practitioner].
- Hacker News "Typst 0.14" thread, split: "LLMs do a pretty good job of generating Typst code" (imiric) vs "they do a terrible job with Typst" (nonethewiser); ChatGPT errors from using `#` as comment (bluenose69); "Claude did generated a rather good template" (vrotaru) [source: https://hn.svelte.dev/item/45693978 | HN: Typst 0.14 (mirror) | practitioner].
- Skill files work around this: typst-writer skill says "Never assume syntax from other languages applies", "Verify uncertain syntax", "NO tuples - Typst only has arrays" [source: https://skills.sh/ypares/agent-skills/typst-writer | typst-writer skill | practitioner].
- Breaking changes inside Touying itself: 0.8.0 upgrade notes say a `#pause` after `uncover`/`only`/`alternatives` "no longer skips the subslides they reserve", footnote-bibliography config "changed shape", `semi-transparent-cover` deprecated [source: https://github.com/touying-typ/touying/blob/main/README.md | Touying README | vendor].

Contradiction: practitioner reports range from "pretty good" to "terrible" (HN), with forum users saying Claude needs "minor adjustments"; the one large benchmark (TeXFix-Bench) measures repair, not authoring, and the one authoring benchmark (TypstBench) has 23 tasks and a disputed scoring method. No controlled benchmark of LLMs writing Touying slides was found.

## SQ3: What do agents and LLM tools do better with text forms (Markdown, Typst, HTML) than with JSON trees, and what is known about round-tripping a text form with a positioned/canvas model (Slidev's visual editing, Marp, reveal.js, Quarto revealjs, Spectacle)? Any prior art for a deck that has both a JSON source of truth and a text projection?

### Text vs JSON output: general evidence

- Aider (2024-08-14): four models (claude-3-5-sonnet-20240620, deepseek-coder V2 0724, gpt-4o-2024-05-13, gpt-4o-2024-08-06), 133 problems, 5 runs each; all scored lower when code was wrapped in JSON than in Markdown; gpt-4o-2024-05-13 dropped only 0.4 points; strict JSON mode did not help; "LLMs are bad at returning code in structured JSON responses" [source: https://aider.chat/2024/08/14/code-in-json.html | LLMs are bad at returning code in JSON | practitioner].
- "Let Me Speak Freely?" (Tam et al., arXiv 2408.02442, v3 2024-10-14): "we observe a significant decline in LLMs reasoning abilities under format restrictions" and "stricter format constraints generally lead to greater performance degradation in reasoning tasks" [source: https://arxiv.org/abs/2408.02442 | Let Me Speak Freely? | independent].
- Counter-evidence: .txt re-ran the tasks with Llama-3-8B-Instruct and got structured ≥ unstructured (GSM8K 0.77 vs 0.78; Last Letter 0.73 vs 0.77; Shuffle Object 0.41 vs 0.44); argues the paper used different prompts per format, a JSON prompt that never mentioned JSON, and an AI parser that confounded scoring [source: https://blog.dottxt.ai/say-what-you-mean.html | Say What You Mean | vendor].
- JSON Whisperer (EMNLP 2025 Industry): "array manipulations require tracking index shifts across operations, which LLMs handle poorly"; EASE "transforms arrays into dictionaries with stable keys, eliminating index arithmetic complexities"; patch generation with EASE cut tokens 31% with edit quality within 5% of full regeneration (figures from search summary of abstract) [source: https://arxiv.org/abs/2510.04717v1 | JSON Whisperer (Duanis, Greenstein-Messica, Habba, 2025-10-06) | independent].

### Slide-specific evidence on representation

- Brosse (2025-08-15, updated 2026-08-22), Gemini 2.5 Pro rebuilding five slides in HTML/CSS, Quarto revealjs, Google Slides API and python-pptx: "The model therefore cannot produce the deck; it can only produce a program that produces the deck" (of API formats); "Every defect in the `python-pptx` deck was silent"; "Quarto/Reveal.js is the practical choice today"; "The gap is tooling, not models"; Quarto source about seven times shorter than the Slides script; single author, one deck [source: https://nbrosse.github.io/posts/llm-slides/llm-slides.html | LLM-Powered Slide Decks: A Comparison of Formats | practitioner].
- ACE (Jang, Lee, Park, Kwak; arXiv 2608.24103, 2026-08-25): hierarchical scene graph with 98 semantic tools; on 53 cases IF/VQ: ACE (gpt-5.5) 4.74/4.19, ACE (claude) 4.45/4.02, "Claude-Skill HTML" baseline (Claude Code editing a per-deck `index.html`) 4.09/3.89 at 203.0 s and $0.968, PPTArena (OOXML/python-pptx) 2.38/2.30; full 94 tasks IF 4.23 vs HTML 3.81 (p = .010); VQ not significantly different from HTML; ablation scene graph 4.04/3.75 vs OpenXML 3.40/3.13 [source: https://arxiv.org/html/2608.24103v1 | ACE: Self-Correcting Agentic Canvas Editor | independent].
- ACE on absolute layouts: OOXML's absolute EMU offsets give a "coordinate-pushing" regime that produces spatial hallucinations when content is inserted or removed; python-pptx code editing depends on the model's absolute-coordinate arithmetic [source: https://arxiv.org/html/2608.24103v1 | ACE | independent]. Listed affiliations are Seoul National University and Miridih (Miridih is not described in the paper) [source: https://arxiv.org/html/2608.24103v1 | ACE | independent].
- PPTArena (Ofengenden et al., UIUC; arXiv 2512.03042 v3, 2026-07-02): PPTPilot routes 66% of edits to python-pptx and 34% to direct XML; ablation IF/VQ: XML-only 0.95/2.85, python-pptx-only 2.06/2.73, hybrid 2.36/2.69, hybrid with 3x refinement loop 2.84/3.21; "when modifications span many slides, the programmatic approach is significantly more reliable" [source: https://arxiv.org/html/2512.03042 | PPTArena: A Benchmark for PowerPoint Editing | independent].
- tldraw's agent starter kit gives the model a simplified JSON projection, not raw records: `FocusedShape` (type, x, y, w, h, color, fill, text, `note`, `shapeId`), `BlurryShape` (id, type, text, box) and `PeripheralShapeCluster` (bounds, count) for shapes outside view [source: https://github.com/tldraw/tldraw/tree/main/templates/agent/shared/format | tldraw agent template formats | vendor]. Docs: context is a viewport screenshot plus "Simplified representations of shapes within view"; a sanitization layer "corrects shape IDs that don't exist, ensures new IDs are unique, and normalizes coordinates" [source: https://tldraw.dev/docs/ai | tldraw: AI integrations | vendor].

### Round-tripping a text form with a canvas: prior art found

- Slidev Studio (`slidev-addon-studio`, MIT, 58 stars, created 2026-08-19): "Markdown is the source of truth. Every action in Studio is a small, readable edit to your `.md` file. There is no project format, no database"; dragging a block "leaves the document flow: Studio wraps it in Slidev's own `v-drag`, so the position is written into the Markdown as `pos="x,y,w,h"` in slide canvas units"; snapping to edges, centre, thirds and other elements [source: https://github.com/BobTheShoplifter/slidev-addon-studio | slidev-addon-studio README | vendor].
- Studio text editing: "What is edited is the block's Markdown, not its rendered HTML"; "Round-tripping rendered HTML back into Markdown is where visual editors lose components, directives and formatting"; a block is edited on the slide only "when its markup can be written back to Markdown exactly; anything else ... opens as Markdown instead" [source: https://github.com/BobTheShoplifter/slidev-addon-studio | slidev-addon-studio README; PR 2709 | vendor].
- Studio limits: text in layout frontmatter keys (e.g. `layout: fact` `value:`/`label:`) "never passed through Markdown, so there is nothing on the canvas to click"; undo "replays a whole slide by its number, and after a renumbering those numbers point somewhere else", and adding, duplicating, deleting, reordering or skipping a slide clears it [source: https://github.com/BobTheShoplifter/slidev-addon-studio | slidev-addon-studio README | vendor].
- Studio's license read from file: "MIT License / Copyright (c) 2026 Daniel Christensen" [source: https://github.com/BobTheShoplifter/slidev-addon-studio/blob/main/LICENSE | slidev-addon-studio LICENSE | vendor].

- Slidev core `v-drag` writes positions back into Markdown by regex (see SQ1) [source: https://sli.dev/features/draggable | Slidev: Draggable Elements | vendor].
- Tylina keeps `.typ` source canonical under a WYSIWYG view; edits on complex content open source and apply only after a successful compile (see SQ2) [source: https://tylina.github.io/ | Tylina | vendor].
- Quarto visual editor: "generates markdown using Pandoc"; normalizes source (prefers `*text*`, rewrites links, list spacing, footnotes); "`canonical: true`" means "edits in visual mode and source mode will result in identical markdown output"; some Pandoc extensions unsupported; non-YAML title blocks make "visual mode ... fail to load with a warning" [source: https://quarto.org/docs/visual-editor/markdown.html | Quarto: Visual Editor Markdown Output | vendor]. - Quarto revealjs positions in text: "The `absolute` class lets you position elements at arbitrary positions on a slide" with `top`, `left`, `width`, `height` attributes; auto-animate matches elements by content or `data-id` [source: https://quarto.org/docs/presentations/revealjs/advanced.html | Quarto: Advanced Reveal | vendor].
